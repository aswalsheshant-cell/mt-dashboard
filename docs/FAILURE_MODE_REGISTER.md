# Failure-Mode Register

Created 2026-09-13. This catalogues failure PATTERNS found in this project so far,
each with its preventive control, not just its one-off fix — so the same class of
defect is caught before it reaches the dashboard next time, rather than rediscovered
from scratch in a future session. Add a new `FM-NN` row whenever a material defect
is found; do not delete a row once a pattern has occurred, even after the specific
instance is fixed — the control is what stays permanent.

Every row below is a REAL incident from this repository's own history (not a
hypothetical), each already fixed at least once. Preventive controls marked
`NOT YET BUILT` are honestly flagged as such, not claimed as done.

## Error-to-pattern routing (the "trace to the earliest wrong layer" rule)

Added 2026-09-13. When a number looks wrong, trace it through the layers below in
order and fix the **earliest** one that's actually broken — never patch a later
layer (a chart, a card, a rendering tweak) to paper over an error that originated
upstream:

```
Source file -> Schema/grain -> Master-data mapping -> Allocation ->
Canonical fact (data.js block) -> Registered measure (docs/METRIC_REGISTRY.md) ->
Filter/comparison logic -> Rendered visual
```

## What this register is NOT

This is a documentation-level catalogue, not an automated pre-flight validation
system. A 2026-09-13 request asked for a much larger preventive-engineering
program (per-dataset data contracts, monthly source fingerprinting, an automated
source-conflict detector, specialized sub-agent roles for source integrity/
mapping/finance-methodology/semantic-relationships/dashboard-QA/release-gating,
and machine-readable project state beyond what `docs/PROJECT_STATE.md` already
provides). Building all of that in one pass would mean either doing it shallowly
(defeating the point) or claiming controls exist that don't -- neither is
acceptable under this project's no-fabrication rule. What IS built, real, and
running today:

- `config/data_source_registry.yml` + `scripts/data_catalog.py` -- source
  registration and lookup (built in an earlier pass, extended since).
- `scripts/ci_validate_datajs.py` -- the closest thing to a release gate today:
  JSON validity, baseline invariants, detail-coverage regression (FM-03), and
  stale-metadata divergence (FM-05).
- `tests/test_pl_expense_input_filter.py` -- the one dedicated regression test
  born directly from a failure mode (FM-01).
- This register -- the FM catalogue itself.

What is recommended but **not built** this pass, so a future session does not
mistake documentation for implementation: automated schema-drift diffing per
new monthly file, source fingerprinting, a dedicated returns-rate control,
pre-ingestion source-conflict scanning, and the specialized sub-agent roles.
Each is a genuinely separate, scoped implementation task -- listed here so the
next session picks up from an accurate starting point rather than re-deriving
whether they exist.
